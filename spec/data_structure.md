# data structure 

> (from planning strategy)

> - 단순한 학습 예정 항목의 나열이 아닌 분석 가능한 `계획 - 실행 - 회고 루프`와 학습을 위한 시간·공간을 관리하는 방법론
> - 의도와 형태, 그리고 이를 뒷받침하는 데이터/화면 기준을 명확하게 서술한 전략 문서
> - 내 설명을 Gemini argon을 통해 문서화시킨 상태 (재검증 루프 필요)

---

## 1. 핵심 루프 및 도메인 철학

```
[계획 (Plan / Node)] ──> [실행 및 기록 (Time / Metric / Check)] ──> [유지 및 회고 (Review / Dashboard)]
       ▲                                                                        │
       └────────────────── 만료·정착률·시간 통계 기반 다음 계획 보정 ───────────────┘
```

- `무계획 실행 허용`: 계획 없이 즉시 수행한 학습이나 기록도 동일한 트리의 하위/중간 노드에 매달려 통계와 복습 회고로 이어져야 한다.
- `기록의 통합 소유`: 시간(학습·업무), 수치(체중·운동·수면·점수), 진도(할 일·단원 체크)를 파편화된 도구가 아닌 단일 계층 트리 위에 통합 관리한다.

---

## 2. 다계층 통합 트리 구조 (Planning Hierarchy)

### 2-1. 기본 대분류 및 독립적 깊이
- `초기 대분류 3축` (`depth = 1` 기본 프리셋, 유저 수정·추가 가능)
    - `개인 (Personal / Life)`: 수면, 식사, 운동, 체중/인바디, 취미 (예: 2단 — `개인 > 체중`)
    - `업무 (Work)`: 알바, 프로젝트, 직무 (예: 3단 — `업무 > 알바 > 근무`)
    - `학습 (Study)`: 전공, 시험, 어학, 자격증 (예: 5단 이상 — `학습 > 전공 > OS > 3장 > 정리`)
- `가변 깊이 원칙`
    - 대분류마다 요구하는 깊이가 다르므로 고정 단계 테이블(`depth1~5`)을 두지 않고, `자기참조 트리 (parent_id)`를 사용한다.
    - 사용자는 1단(단일 항목)부터 N단까지 원하는 깊이 어디에나 직접 기록을 연결할 수 있다.

### 2-2. 노드별 기록 타입 (`record_type`)
각 노드는 자신이 어떤 방식으로 기록되는지 안내판 역할을 하는 `record_type`을 가진다.
- `GROUP` : 하위 노드를 묶는 순수 분류 폴더 (하위 기록 합산 집계 대상)
- `CHECK` : 완료 여부(`is_done`)로 관리하는 진도/할 일 (페이지, 문제집, 단원 등 — 수치 그래프 대상 아님)
- `TIME` : 타임 트래커로 시간을 측정하는 대상 (`is_done` 체크와 병행 가능)
- `METRIC` : 날짜별 단일 수치를 입력하는 대상 (`unit` 단위 포함: `kg`, `%`, `점`, `회`, `h` 등)

## 3. 시간 관리 및 실행 측정 전략

### 3-1. Time Tracker 측정 구조 (병렬 스플릿 모델)
- `단일 세션 + 계층 자동 합산 (Roll-up)`
    - 5중 타이머를 따로 돌리지 않고, 사용자는 `현재 공부할 노드 1개`만 선택해 단일 타이머를 실행한다.
    - 집계 시 노드 경로를 따라 상위(`단원 → 과목 → 분야 → 대분류 → 전체`)로 자동 합산된다.
- `병렬 스플릿 (time_logs + time_splits, 스피드런 방식)`
    - `큰 타이머 (time_logs)`: 전체 시험 또는 전체 학습 세션의 총 경과 시간을 백그라운드에서 계속 측정
    - `세부 스플릿 (time_splits)`: 실행 중 버튼(`Lap`/`Split`)을 누를 때마다 구간 시간과 사용자 지정 라벨(`Name`)을 병렬 기록
    - 문항별·지문별·과목별(수능 등) 측정이 모두 사용자 입력 라벨 하나로 동일하게 대응된다.
- `정확도 보장 원칙`
    - `1초 +1` 카운터 대신 `started_at` 타임스탬프 차감 방식을 기본으로 하여 백그라운드 전환·분할화면에서도 오차가 없도록 한다.

### 3-2. 수치형 트래킹 (`Metric Log`)
- `대상`: 체중(인바디: 체중/골격근량/체지방률), 운동, 수면·컨디션, 시험 점수
- `제외`: 읽은 페이지·푼 문제 수 등 진도 항목은 수치가 아니라 `CHECK` 타입 노드의 완료 상태로 관리한다.

## 4. 알림 전략: 루틴(Routine) vs 복습(Review)의 분리 근거

둘 다 주기적 알림을 발생시키지만 `발생 기준과 미이행(실패) 처리 방식이 정반대`이므로 완전히 다른 도메인으로 분리한다.

### 4-1. 루틴 (Routine) — "생활·투입의 리듬 유지"
- `발생 기준 (절대 시간 고정)`
    - 달력과 시계에 고정된다. (예: 매일 `07:00` 기상, 월·수·금 `19:00` 운동)
    - 시험기간, 학기, 계약 기간 등 `유효 범위 (Start ~ End Date)`를 가질 수 있다.
- `미이행 시 처리 (누적 안 됨 / 리셋)`
    - 어제 루틴을 못 했다고 오늘 2배로 쌓이지 않는다. 어제는 미달성(`Skip`)으로 남고, 오늘은 원래 주기에 맞춰 새로 시작된다.
- `생명주기`: 유효 기간 동안 끝없이 반복되는 무한 루프 (`새로운 실행을 여는 트리거`)

### 4-2. 복습 (Review Reminder) — "학습 기억의 망각 방지"
- `발생 기준 (직전 완료 시점 기반 상대 계산)`
    - 달력이 아니라 `실제로 학습 기록이 끝난 시점`에서 파생된다. (예: 완료 후 `+1일 → +3일 → +7일 → +14일`)
- `미이행 시 처리 (누적 및 3회 만료 규칙)`
    - 오늘 할 복습을 미루면 사라지지 않고 대시보드에 계속 누적(`OVERDUE`)된다.
    - 다음 복습일은 원래 예정일이 아닌 `실제로 복습을 완료한 날` 기준으로 재계산된다.
    - `3회 만료 규칙 (overdue_count >= 3)`: 복습 타이밍을 3번 어기면 기억이 휘발된 것으로 간주하여 `EXPIRED` (만료된 학습) 상태로 전환하고 활성 복습 큐에서 제거한다. (좀비 리스트 누적 방지)
- `생명주기`: 정해진 회차 완료 시 `GRADUATED`(졸업), 3회 실패 시 `EXPIRED`(만료)로 끝나는 유한 루프 (`기억 정착 및 회고 트리거`)

### 4-3. 만료된 학습 데이터(`EXPIRED`)의 회고 활용
- 복습이 `EXPIRED` 처리되어도 과거에 투입한 `time_logs` 시간 기록은 삭제되지 않고 유지된다.
- `회고 지표 산출`: `"완료한 학습 중 졸업(정착) 비율 vs 만료(휘발) 비율"`을 통해 무리한 진도 계획 여부를 판단하는 핵심 근거로 활용한다.
- `유저 후속 액션`: 만료 보관함에서 `재학습 (1회차로 복구)` 또는 `아카이브 (폐기)` 중 선택한다.

## 5. 공간 및 반응형 레이아웃 전략 (Space Management)

### 5-1. 기기 기준이 아닌 `Window Bounds (dp)` 기준 분기
- 갤럭시 S, 탭, 탭+, 탭U 등 기기 모델명이나 `smallestScreenWidthDp`로 분기하지 않고, 분할화면(2·3분할)과 팝업창에 자동 대응하도록 `현재 앱 창에 할당된 width / height dp`만 기준으로 삼는다.

### 5-2. 스마트폰 기준점 (`width = 360dp`) 및 여백 고정 원칙
- `기준 해상도`: 갤럭시 S 기본 세로(`width = 360dp`)를 설계 기준점으로 삼고 정보량을 맞춘다. (세로 길이는 스크롤이 기본이므로 일반 모드에서는 따지지 않음)
- `고정 토큰 vs 가변 폭`
    - 화면 외곽 패딩(`16dp` / Medium 이상 `24dp`), 위젯 간 간격(`12dp` / `16dp`), 위젯 내부 패딩(`16dp`)은 `고정`한다.
    - 화면 폭이 넓어질 때 남는 dp는 여백이 아니라 `위젯의 가로 너비 자체`를 늘려 흡수한다.
- `대시보드 그리드 규격 (360dp 2열 기준)`
    - `1×1` 소형 위젯: `158 × 158dp` (내부 가용 `126 × 126dp` — 제목 1줄 + 핵심 숫자/게이지 1개 + 보조 라벨 1줄 상한)
    - `2×1` 가로 위젯: `328 × 158dp` (좌우 요약+3줄 리스트 또는 주간 7일 막대/추이 그래프)
- `열 수 확장 공식`: `columns = (가용 폭 / 160dp).floor()` (분할화면·태블릿 세로·가로에서 `2열 ~ 5열` 자동 가변)

### 5-3. 네비게이션 및 높이 예외 분기
- `일반 화면 (height >= 480dp)`
    - `width < 600dp` (폰 세로, 태블릿 3분할): 상단 `AppBar` + 하단 `NavigationBar`
    - `width >= 600dp` (태블릿 세로/가로, 2분할): 좌측 `NavigationRail` (`840dp+`에서 Drawer 확장 토글) + 상단 `AppBar`
- `유일한 높이 분기 (height < 480dp)`
    - 스마트폰 가로 모드 또는 상하 분할화면: 하단 바 제거 및 좌측 `NavigationRail` 강제 전환 + `AppBar` 최소화

## 6. 데이터 저장 및 동기화 기본 원칙 (DBMS Reference)

### 6-1. 핵심 테이블 구성
- `nodes` : 계층 트리 본체 (`id`, `parent_id`, `root_id`, `path`, `title`, `record_type`, `unit`, `is_done`)
- `time_logs` : 타이머 및 직접 입력 시간 기록 (`id`, `node_id`, `duration_sec`, `started_at`, `ended_at`)
- `time_splits` : 병렬 스플릿 랩 타임 (`id`, `time_log_id`, `label`, `split_duration_sec`, `recorded_at`)
- `metric_logs` : 수치 트래킹 기록 (`id`, `node_id`, `value`, `recorded_at`, `memo`)
- `routines` : 절대 시간 고정 반복 일정 (`id`, `node_id`, `cron_or_days`, `valid_from`, `valid_to`)
- `review_items` : 상대 주기 복습 큐 (`id`, `node_id`, `stage`, `next_review_at`, `overdue_count`, `status`)

### 6-2. 계층 집계 방식 (`Materialized Path`)
- `nodes.path`에 조상 경로(예: `"/1/2/3/"`)를 함께 저장하여, 재귀 쿼리(`WITH RECURSIVE`) 없이 `WHERE n.path LIKE '/1/2/3/%'` 한 줄로 임의 깊이의 하위 시간·진도를 즉시 집계한다.

### 6-3. 전 테이블 동기화·복구 공통 컬럼
오프라인 우선(Local SQLite) 저장 후 기기 간 동기화 및 휴지통 복구를 지원하기 위해 모든 테이블에 아래 4개 컬럼을 필수로 둔다.
- `id` : `UUIDv7` (오프라인 다중 기기 동시 생성 시 PK 충돌 방지 및 시간순 정렬 보장)
- `created_at` : 생성 일시
- `updated_at` : 수정 일시 (증분 동기화 및 충돌 판단 기준)
- `deleted_at` : 삭제 일시 (`NULL`이면 활성, 값 존재 시 Soft Delete — 삭제 전파 및 복구 가능)
